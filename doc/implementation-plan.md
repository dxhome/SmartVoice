# SmartVoice Implementation Plan

**Last reviewed:** 2026-10-03

This plan reflects the current code and product scope. It separates the implemented local-service baseline from the next P1 capability and the P2 verification and expansion work. For architecture principles, implementation summary, and the centralized backend/platform compatibility matrix, see [architecture-guidelines.md](architecture-guidelines.md); for HTTP behavior, see [api-spec.md](api-spec.md); for test commands, see [testing.md](testing.md).

## Priority Definitions

- **P0 — Current baseline:** The basic local speech service and its architecture are implemented. There are no known uncompleted P0 implementation items in this plan.
- **P1 — Next product capability:** Streaming STT, translated subtitles, and spoken interpretation.
- **P2 — Acceptance and expansion:** Formal quality/performance acceptance, verification of the Windows/Linux model-platform matrix, and remaining platform, runtime, security, packaging, and product extensions.

P2 work is planned but is not a promise that every item will ship in the next release. Confirm platform targets, measurable thresholds, and release scope before starting an item.

## Current Implemented Baseline

The current product is a local CPU speech service. It exposes REST endpoints for health/readiness, runtime/capability and model discovery, model catalog/lifecycle, file transcription, and WAV synthesis. STT and TTS use the `smartvoice-auto` virtual model for language-aware routing or a concrete installed model ID for direct calls. Routing configuration is validated and can be reloaded while the service runs.

The code is divided into API, application services, domain contracts, ports, and platform/inference/storage adapters. Model lifecycle includes catalog-backed installation jobs, cancellation and download resume, model file verification, removal, and verified offline package import/export. The service defaults to loopback, bounds inference requests, and reports runtime and request diagnostics.

The regression suite runs functional/API tests and real CPU inference via REST routes. Its routed integration cases exercise service/model discovery, routed and direct STT, Chinese/English speech-language detection, supported input audio formats, invalid audio, routed/direct TTS, automatic TTS language detection, and long-text synthesis when their required models/assets are installed. It also generates a direct smoke test for every catalog model and runs it for each installed model whose runtime is available; absent models are reported as skips. Run `python scripts/test.py ci` for CI and `python scripts/test.py regression` for local regression with SmartVoice installed and any desired models present.

Current platform and backend compatibility is summarized in [architecture-guidelines.md](architecture-guidelines.md); installation state and current inference availability are separate. Source-install paths and release wheel builds cover Windows x64, macOS Apple Silicon, and Linux x86_64. Linux x86_64 has passed clean installation and model-backed inference validation on Ubuntu 26.04. Other Linux distributions and Linux arm64 are not yet verified. Android is not supported. GPU inference, streaming sessions, remote/LAN access, and a management UI are not part of the current baseline.

## P1 — Streaming STT, Translation, and Interpretation

### Goal and modes

Add a session-oriented capability that continuously receives audio and returns incremental results in three modes:

1. **Streaming transcription:** Return partial and final text in the source language.
2. **Translated subtitles:** Return translated text, with optional source transcript and source/translation alignment.
3. **Spoken interpretation:** Return translated text and ordered, chunked synthesized audio. Speak only committed translations that are stable enough to avoid retracting already-played speech.

Keep the existing file-based `POST /v1/audio/transcriptions` behavior. Streaming is a separate session API and must not change the semantics of existing one-shot endpoints.

### Current code boundary and required extension

The current implementation already has useful seams: HTTP routes call application services; `TranscriptionService` and `SpeechService` own one-shot routing and orchestration; `InferenceProvider` and `ModelRepository` are provider-neutral ports; `CompositeInferenceProvider` selects an inference adapter by model ID; catalog entries define installed assets, task/language metadata and backend; provider capabilities report available runtime support. The current `InferenceProvider.transcribe()` accepts a complete `bytes` payload and returns a completed `TranscriptionResult`; `synthesize()` returns a completed audio result. Neither exposes a live stream lifecycle, incremental results, translation, or chunked audio generation. `TaskName`/`TaskCapability` describes the existing model operations (transcription and speech synthesis), not complete user workflows, while the normal application services and `InferenceQueue` handle finite requests.

Do not retrofit live sessions by repeatedly invoking file transcription on expanding partial buffers, or by holding a normal `InferenceQueue` permit for the lifetime of a WebSocket. A bounded, completed utterance may use existing offline transcription through an explicit utterance strategy; it cannot advertise native partial recognition. Add a focused streaming-session application service and focused streaming ports only after confirming selected runtime/model behavior. The session service resolves a complete processing plan, holds its model-use protection, owns session policy and coordinates the stages; the transport handler validates frames and serializes events. A provider-neutral streaming port should express session operations such as opening a configured stream, accepting normalized audio frames, retrieving incremental results, finishing/canceling, and releasing resources. Keep sherpa-onnx stream/recognizer objects and frame/decode details inside its adapter. Use the current `CompositeInferenceProvider` pattern as a guide for selecting runtime adapters per model, but do not assume that synchronous `InferenceProvider` implementations can satisfy a streaming port. Translation and chunked speech output need focused replaceable capabilities when a selected cascade uses separate models. Reuse `ModelRepository` and its verified install/uninstall lifecycle, extending catalog/model metadata rather than creating a parallel asset registry.

Represent the three user workflows as a separate, versioned session capability (`transcription`, `translated_subtitles`, `spoken_interpretation`), not as new values in the existing model `TaskName` unless a concrete catalog use case requires it. Model artifact capabilities and end-to-end session modes are different: a mode may resolve to an ASR + translation + TTS chain or one end-to-end model. Extend typed contracts and capability discovery to describe supported session modes, input/output modalities, source/target language or language-pair coverage, interim/final behavior, and unavailability reasons. Keep model-level fields for runtime/model traits and workflow-level fields for complete usable plans. Do not infer features from `model_type`, backend name, or catalog ID. Preserve one-shot `TranscriptionService`/`SpeechService` behavior and existing REST compatibility.

### Work sequence

1. **Draft the session contract and validate inference strategies.** Compare native online ASR with built-in endpointing against VAD-segmented offline ASR in the sandbox. Draft session creation fields, modes, source/target languages, model selection, partial/final semantics, event envelopes, timestamps, audio format, errors, finish/cancel, disconnect behavior, and versioning; freeze v1 after the runtime spike. Use a WebSocket API unless implementation discovery establishes a concrete reason to choose another transport.
2. **Validate the model chain and runtime integration.** Evaluate streaming ASR, translation, and TTS options for each initial language pair, including model files, licensing, runtime API/thread-safety, Windows x64, macOS Apple Silicon, and Linux x86_64 integration, model size and actual target-device performance. Do not infer SmartVoice support from upstream sherpa-onnx platform claims; validate the exact Python/native artifact and each model on SmartVoice's documented targets. A mode may use a cascade or a single end-to-end model, but model/runtime details must remain behind adapters. Define capability metadata and validate that a complete chain is available before starting a session.
3. **Define streaming-specific application and adapter boundaries.** Add the session orchestrator and focused live-stream inference capability separately from `InferenceProvider`, `TranscriptionService`, and `SpeechService`. Reuse `CompositeInferenceProvider`'s model-ID-to-adapter selection concept where appropriate. Decide whether each online recognizer instance can safely serve multiple live streams, how each session maps to stream state, and whether the adapter needs per-instance locking, per-session execution or bounded micro-batching. The current `ElasticRuntimePool.run()` leases an instance for one finite operation and releases it after native execution; it has no live-session affinity API. Native ASR stream state must stay attached to its owning recognizer throughout the session rather than borrowing an arbitrary pool instance per frame. Start with bounded dedicated online recognizer ownership; evaluate safe sharing later. Translation, offline utterance ASR and segment TTS borrow finite-operation capacity only while working. Protect all models in the pinned chain against removal without reserving every stage's execution capacity for the entire session. Keep streaming admission/scheduling separate from ordinary queue permits, but budget both against shared CPU/memory and runtime locks. Do not change one-shot concurrency defaults based on streaming assumptions.
4. **Build bounded session infrastructure.** Define per-session recognition state, fair scheduling, session quotas, audio buffering, backpressure, idle/maximum lifetime, output limits, cancellation, disconnect cleanup, service shutdown, overload, and slow-client handling. Long-lived sessions must not occupy the ordinary one-shot inference queue indefinitely.
5. **Implement the modes incrementally.** Start with source-language partial/final transcription. Add translated subtitles after model and language-pair validation. Add interpreted audio only after translation commitment, chunk ordering, cancellation, and backlog behavior are defined.
6. **Accept each mode independently.** Measure first-partial and final latency, translation revisions, first-audio latency, sustained real-time factor, WER/CER and translation quality, CPU/memory, session capacity, and behavior under cancellation, disconnect, overload, and shutdown.

For native online ASR, evaluate built-in endpoint detection first and keep external VAD optional. For the offline utterance strategy, provide VAD or another explicit bounded segmentation policy. Choose defaults per strategy from measured results, rather than applying one VAD rule to every processing plan.

### Inference strategies and reference findings

Keep user modes independent of inference strategy. The same session infrastructure normalizes audio, tracks its sample timeline, applies segmentation/commit policy and schedules downstream stages:

| Strategy | Model invocation | Visible output | Recommended priority |
|---|---|---|---|
| Native online ASR | Maintain one native stream; accept frames, decode when ready, retrieve hypotheses, finalize/reset at an endpoint, and drain on input finish. | Revisable partial text and committed utterance text. | Main path for live original-language subtitles. |
| Offline utterance ASR | Preserve bounded audio until VAD/policy completes an utterance; submit that segment once to an offline recognizer. | Text after segment completion; no genuine intra-utterance partials. | Early sandbox comparison and an explicitly advertised compatibility option. |
| Two-pass ASR | Online first pass followed by optional offline correction of a bounded segment. | Early hypotheses and later corrections under a defined commit policy. | Later experiment; do not revise translations already spoken. |

The static reference review of QSmartAssistant at commit `57291d44e28d5e56fbd16041b2f02472508eeba7` supports this separation. Its [Sherpa ASR adapter](https://github.com/xinhecuican/QSmartAssistant/blob/57291d44e28d5e56fbd16041b2f02472508eeba7/Conversation/ASR/sherpaasr.cpp) creates a real online recognizer in online mode, but its outward recognition signal is emitted on input completion rather than for every partial hypothesis. Its [conversation orchestration](https://github.com/xinhecuican/QSmartAssistant/blob/57291d44e28d5e56fbd16041b2f02472508eeba7/Conversation/conversation.cpp) supports frame-fed online ASR or buffered offline ASR. Its [Sherpa TTS adapter](https://github.com/xinhecuican/QSmartAssistant/blob/57291d44e28d5e56fbd16041b2f02472508eeba7/Conversation/TTS/sherpatts.cpp) generates complete segment waveforms with offline TTS; incremental delivery comes from text segmentation and ordered playback. These are useful implementation patterns, not evidence of translation support, SmartVoice multi-session safety, or measured performance.

Preserve silence/context needed by the recognizer: the reference [VAD audio path](https://github.com/xinhecuican/QSmartAssistant/blob/57291d44e28d5e56fbd16041b2f02472508eeba7/Wakeup/wakeup.cpp) feeds audio blocks while using detection to end an utterance. SmartVoice should likewise distinguish segmentation from audio suppression. Use bounded pre-roll/end padding and speech-duration/silence-duration counters on the audio sample timeline; wall-clock arrival gaps must not be mistaken for silence. A continuous-speech maximum segment duration must force a controlled boundary rather than allow unlimited buffering. Utterance completion keeps the session open; `finish_input` drains pending ASR, translation and TTS before session completion.

For spoken interpretation, first use committed translation segments with existing whole-segment TTS. Overlap recognition of newer audio, translation of completed source segments, synthesis of earlier translations, and client playback. A segment may be sent in transport chunks after synthesis completes; describe this as segment-based audio delivery, not native incremental acoustic generation. Segment commitment should consider source stability, linguistic boundaries, minimum/maximum length and maximum wait; punctuation alone is insufficient for numbers, abbreviations and cross-language word order. Initial commitment may wait for a source utterance final; earlier stable-prefix commitment requires separate evidence. Coalesce superseded uncommitted work, preserve committed output order, and limit speech backlog by estimated or actual audio duration as well as bytes/items. Native incremental-text TTS, ASR micro-batching and end-to-end speech translation remain later research directions.

### Session and event contract details

- Session creation declares the mode, source language (explicit or auto), target language when translation is enabled, whether source text should be returned, and model/routing selection. Pin the selected processing chain and policy for the lifetime of the session and report it in `session-ready`.
- Recommended transport shape for the first protocol version: one versioned WebSocket session endpoint under `/v1/audio/` with an initial JSON configuration/control message, ordered audio frames, and JSON result/control events. Prefer binary PCM audio frames over base64; declare encoding, sample rate, channel count, monotonically increasing frame sequence and end-of-stream explicitly. Normalize audio once at the session boundary and share it across ASR/VAD stages. Fix the initial accepted wire format after the first client/runtime spike; do not expose runtime-specific frame sizes. For spoken interpretation, pair each binary output audio frame with a preceding JSON descriptor carrying segment ID, sequence, encoding/rate/channels, and completion state. Reconnection/resumption can be out of scope for v1 if session cleanup is deterministic.
- Define server events for session readiness, source-language partial/final text, target-language partial/final translation, target audio chunks, utterance completion, session completion, and errors. Events carry session ID, utterance/segment ID, language, finality, and available time ranges.
- Link translated segments to their source segments and generated audio chunks to the translation segments they speak. Specify encoding, sample rate, channels, sequence/order, and how the client detects missing or completed chunks.
- Define session finish/cancel, heartbeat, idle and maximum lifetime, disconnect behavior, error envelope, recoverability, and protocol versioning. Set explicit limits for audio chunk size, duration, session count, and input/output buffering.
- Keep model and runtime specifics out of the public event schema. The session API expresses capabilities and output semantics; adapters own streaming recognizer, translator, and synthesizer objects.
- Keep a clean compatibility boundary: the existing synchronous one-shot provider methods and `/v1/audio/transcriptions`/`/v1/audio/speech` endpoints continue to serve finite requests. Streaming code must not place HTTP request/socket objects in application services or domain contracts, nor expose sherpa-onnx frame sizes, recognizer handles, or decoder state to clients.
- Treat model install/verification/uninstall as shared `ModelRepository` responsibilities. Sessions hold a model-use lease or equivalent protection so a model cannot be removed while a session is using it. Pin the resolved processing plan and router/catalog revision for the session; configuration updates affect new sessions, and removal of any model in an active chain is blocked until its lease is released.
- Initialize and shut down streaming session management through the existing application lifespan. Close sessions and release leases before calling provider `RuntimeLifecycle.close()`; shutdown and adapter replacement must not leave native stream handles alive.
- Keep streaming mode discovery distinct from current `/v1/capabilities?task=transcription|speech` model-task discovery. Add an additive/versioned session-mode capability document (or equivalent explicit extension) that reports available modes and compatible plans/language pairs. Do not mark every current catalog model's `streaming` flag true or reinterpret it as end-to-end workflow support.

### Incremental commitment, revision, and endpointing

Streaming recognition may revise partial text as more audio arrives, and a translation may change when its source transcript changes. Define when partial text can be edited, how a stable source segment is committed, how partial and final translations are distinguished, and when a translation is final. Spoken interpretation must only synthesize committed translations because already-played audio cannot be retracted.

Balance translation trigger frequency, revision rate, utterance endpointing, context, quality, latency, and compute cost. Do not run translation or TTS for every ASR partial. VAD and endpointing are separate: VAD detects speech/silence for segmentation or suppression, while ASR endpointing decides when an utterance is ready to commit. Evaluate built-in endpointing first for online ASR; evaluate VAD boundaries explicitly for offline utterance ASR. Measure missed quiet speech, truncation, noise false positives, forced long-speech boundaries, and CPU overhead.

### Streaming model capability and routing details

Current catalog entries for Whisper, SenseVoice, and Qwen3-ASR are offline models; catalog presence does not imply streaming support. Add explicit metadata for online/offline operation, input/output modality, streaming support, source/target language or language pairs, required assets, runtime/platform/device requirements, and license. Evaluate streaming ASR, text translation, speech translation, and TTS as a complete feasible chain for each mode and language pair. If auto language detection cannot finish within the session's latency budget, define a wait state or require an explicit source language; never silently change language or model after user-visible output begins.

The existing `ModelRouter` selects an individual model by task and language. It does not select or validate an end-to-end chain. Add a session processing-plan resolver that uses repository metadata and explicit capability records to produce one compatible plan for `(mode, source language, target language, requested model/policy)`. A plan may contain online or offline-utterance ASR, translation and TTS models, or one model that provides the requested end-to-end mode. Advertise the actual strategy, partial-result support and segment-based versus native audio generation; never silently substitute offline utterance recognition when an online strategy was requested. The resolver must reject incomplete chains before opening the socket and return an explainable unavailable reason. For the first release, prefer a small, explicitly validated language-pair set and deterministic ordered plan configuration; do not imply that existing `router.json` alone can express multi-model compatibility. Existing model-task routing may be reused for a plan member only when its selection cannot result in an incompatible chain.

### Streaming concurrency, resources, and failure semantics

The existing inference queue serves finite one-shot requests. A long-lived session must not occupy an ordinary request slot indefinitely, and incoming audio must not accumulate in an unbounded queue. Design per-session recognizer state, fair scheduling, concurrent-session quotas, model sharing/isolation, bounded audio buffers and output queues, input backpressure, slow-client behavior, and TTS lag/backlog handling. Define cancellation/disconnect cleanup, idle and maximum lifetime, overload responses, shutdown behavior, and what happens to committed versus uncommitted output when a failure occurs.

Measure first-partial and final latency, end-to-end sustained real-time factor, queue latency, CPU/memory, session capacity, and behavior under a fixed-rate load. For translation modes, also measure revision rate, alignment, translation quality, and language-pair latency. For speech output, measure time to first audio, playback order, cancellation, and backlog recovery.

### Sandbox prototype roadmap

Prototype development is isolated under `sandbox/streaming/`; the directory is now implemented, with checkpoints recorded below. Keep experimental adapters, the replay/client harness and dependency pins there until promotion is explicitly scoped. Reuse verified model assets without copying weights into Git. Keep large audio/model/generated artifacts out of version control; retain small manifests, configuration, reference transcripts, event traces and reports with documented corpus rights. Do not publish prototype capabilities as production support.

Proceed through these six stages, retaining a runnable checkpoint and a decision report after each stage. Start on the current macOS Apple Silicon development machine; Windows x64 and Linux x86_64 validation remain required before claiming product support.

| Stage | Prototype deliverable | Decision before advancing |
|---|---|---|
| S0 — Reproducible input and model baseline | Fixed-rate PCM replay harness, input manifest, environment/model pins, candidate inventory and metric definitions. | Inputs, model assets/licenses and execution conditions are reproducible; choose at least one real online ASR candidate and one available offline baseline. |
| S1 — ASR and segmentation comparison | Real online partial/final recognition versus VAD-segmented offline recognition on the same replay audio. | Select the main online path and any worthwhile utterance option using measured quality, latency and resources; document limitations. |
| S2 — Bounded streaming sessions | Prototype WebSocket client/server, event contract, session state and recognizer ownership with cleanup. | Continuous sessions produce aligned results and finish correctly; buffers/capacity stay bounded under interruption and slow consumers. |
| S3 — Readable incremental subtitles | Punctuation/sentence formatting, bounded semantic source commitment, revisable early target text, replaceable real translation adapter and source/target alignment for one validated pair. | Readable source and target captions update during continuous speech; quality, first-target lag, revisions, final commitment and resource budgets pass the S3m and S3a–S3d gates below. |
| S4 — Spoken interpretation | Committed translation segment TTS, ordered audio delivery and sample client playback. | Audio delivery/playback order, first playable audio and bounded backlog/cancellation are measured automatically; intelligibility/listening review moves to S5. |
| S5 — Integration decision and platform evidence | Sustained mixed-load/cleanup report, target-platform checks and a production integration checklist. | Decide what to promote, revise or defer; freeze the supported modes, strategies, language pairs and reference-device acceptance targets. |

**S0 tasks.** Inventory existing installed models and runtime versions before choosing downloads. Record concrete online model assets/API/license and available offline ASR/TTS; translation is a new capability and requires its own candidate selection. Use explicit source language initially. Start the harness with mono PCM signed 16-bit at 16 kHz and configurable frame duration (20 ms is an initial experiment, not a public requirement). Replay at audio real time using a monotonic clock and record sample positions separately from arrival/processing times. Include Chinese/English references, quiet speech, noise, pauses, continuous long speech, names/numbers and a final segment without trailing silence. Define first-partial latency from speech onset, commit delay from reference speech end, translation delay from source commit, first-audio delay from the corresponding source speech end, RTF, CER/WER, CPU/RSS and buffer/backlog duration. Report cold and warm runs separately. Set provisional device-specific performance budgets before comparing candidates; do not invent release SLAs from prototype results.

**S1 tasks.** Exercise a native online recognizer with frame acceptance, ready/decode/result retrieval, built-in endpoint/reset and input-finished drain. Publish changing hypotheses during input, not only at the final call. Compare with a bounded VAD segment buffer invoking existing offline ASR once per completed segment. Evaluate onset pre-roll, end padding, minimum speech and forced maximum duration; keep ASR context/silence unless a measured suppression policy warrants removal. Replay identical audio through both strategies, retain hypotheses/finals and sample-time boundaries, and compare endpoint delay, truncation, accuracy, CPU/RSS and sustained processing time. No expanding-window pseudo-streaming baseline is required. If no online candidate meets the initial budget, record the blocker rather than relabeling utterance output as online partials.

**S2 tasks.** Add the minimal three-mode configuration schema but enable only transcription initially. Separate receive/normalize, inference and output workers so native computation does not block socket reads. Start with one active online session and bounded dedicated recognizer ownership; increase to two only for an explicit isolation/capacity experiment. Implement frame sequence validation, stable session/utterance/revision IDs, sample-time ranges, ready/partial/final/utterance-complete events, finish-input drain, cancel and session-complete. Fix hard input duration/bytes, output queue, idle/lifetime and session-count limits. Replay multiple utterances in one session, disconnect mid-inference, cancel, finish without silence, reject malformed frames and exercise a slow reader. Keep ownership until in-flight native work actually ends; verify teardown returns resource counts to baseline. Use simulated slow stages only to exercise infrastructure and label them as mocks, not quality evidence.

**S3 tasks.** Select one direction such as Chinese to English after real-model feasibility review, then add the reverse direction independently if justified. The completed first checkpoint translates finalized source utterances. The user-facing follow-up now requires readable punctuation and target updates before a whole acoustic utterance finishes; first complete the S3m modularization checkpoint, then implement and evaluate S3a–S3d below before S4. Pin ASR/translation models and policy per session, attach translations to source segment IDs, distinguish revisable target text from committed text, and bound pending translation work. Retain representative outputs for manual bilingual review, especially numbers/names and reordered clauses. Measure source-end-to-target delay as well as the stage's own inference time so final-utterance waiting is visible. Validate actual translation with a real model; mock translations only establish plumbing.

**S4 tasks.** Feed only committed translation segments to a selected existing offline TTS provider and enqueue complete segment waveforms in order. Carry translation/segment IDs and chunk metadata through playback. Overlap independent pipeline stages while preventing stale uncommitted work from filling the queue. Set a maximum pending speech duration and define overload/backpressure behavior; do not silently drop committed speech. Measure first playable audio, gaps, synthesis RTF and backlog growth over sustained input. Exercise slow TTS, cancellation during synthesis/playback and session finish while audio is pending. Client cancellation must stop local playback and clear its queued audio; transport delivery alone does not prove playback. Log server delivery and client playback separately. Record segment-based generation explicitly; native TTS streaming is outside this first prototype.

**S5 tasks.** Complete all human acceptance deferred from S3d/S4: independent bilingual review of actual ASR/formatting/draft/final outputs (including years, names, negation and clause relations), manual speech/clause onset/end annotations and meaningful-first-target latency, plus TTS pronunciation, intelligibility, MOS and listening/segmentation review. Pending ratings and timestamps remain pending; prototype engineering passes do not approve them. Run sustained real-time sessions and mixed one-shot/session workloads on the reference device, including continuous speech, noise/silence, slow clients, downstream failure, overload and shutdown. Use configured input arrival rate rather than an unconstrained fast replay to claim real-time capacity. Confirm model/stream affinity, model-use protection, no early lease release on timeout, stable CPU/RSS and bounded queues. Repeat selected real-model paths on Windows x64 and Linux x86_64 before support claims. Produce a report with pinned environment/assets, commands, event/audio traces, quality observations, per-stage/end-to-end latency and unresolved risks. Map prototype modules to production application services, focused ports, runtime adapters, catalog/session capabilities and lifespan; document which contracts and lifecycle changes are required rather than copying the sandbox wholesale into `src/`.

Priority within this roadmap is S0–S2 first, then S3, then S4. S5 gates production promotion; integration safety findings should also be checked at each checkpoint. Defer two-pass correction, automatic language switching, native incremental-text TTS, speech-to-speech end-to-end models, micro-batching, GPU work and reconnection/resumption until the basic cascade has demonstrated useful quality and bounded latency. Prototype reports must distinguish verified results, provisional settings and pending work.

#### Scope, dependency order and architectural boundary

**2026-10-04 scheduling update:** all human quality/boundary/listening acceptance below moves to S5 by the explicit user decision; engineering checks remain required for S4.

Keep explicit source-language selection and one translation direction (Chinese to English). Retain the existing Chinese/English source-only paths and explicit utterance option. Do not otherwise expand the model inventory or language directions as part of this work; a verified punctuation model needed for S3a and targeted comparisons needed for quality are within scope. All changes first run in `sandbox/streaming/`; a stable sandbox boundary is preparation for production, not production integration itself.

Implementation order: **S3m (modular checkpoint) → S3a (readability) → S3b (early revisable translation) → S3c (decoder-streaming decision) → S3d (combined acceptance) → S4**. Establish observability and contract checks in S3m and extend them throughout; S3d performs final combined acceptance rather than postponing all validation until the end.

Target boundary:

```text
WebSocket transport / stable wire events
    → stream orchestrator: stage handoff, ordering, session lifecycle, backpressure
        → typed stage ports: ASR → text formatting → translation → future TTS
            → model adapters: native objects, tokenizer, runtime-specific conversion
Processing-plan resolver and resource scheduler support the orchestrator.
```

The transport handles configuration/frame validation, ACK/control receipt and serialization. It does not select concrete models, own native inference handles or encode model-specific branches. The orchestrator owns queues, source/target revision and commitment policy, stage lifecycle, stale-work suppression, error propagation and drain/cancel. Adapters report native capabilities and convert model outputs to common records; they do not independently decide application commitment. UI consumes language/stage-neutral events and declared capabilities.

#### S3m — Modularization checkpoint (required before S3a)

**M1: Freeze typed stage and event contracts.** Define audio frames, ASR hypotheses, formatted source units, translation requests/drafts/finals, stage failures and future synthesized-audio results as typed internal records. Include session/unit/utterance IDs, monotonic revisions, explicit source/target languages, hypothesis finality versus application commitment, source event/revision/text-span references, coarse sample coverage, boundary reason and bounded timing/policy metadata. Native recognizers, tokenizer pieces and provider dictionaries do not cross ports. Domain records are transport-neutral; a single serializer maps them to wire events.

Define focused stage operations, for example ASR `push_audio / finish / close`, formatting `update / finish / close`, translation `translate` with optional incremental result delivery plus `close`, and the future TTS `synthesize / close`. Specify initialization/readiness, accepted input, output order, unsupported capabilities, idempotent close, partial-construction cleanup, thread affinity, native ownership and error conversion. Declare cancellation as unsupported/cooperative/native when applicable; a logical timeout does not imply hard native interruption. The TTS contract includes committed text input, language, audio format/sample metadata and segment identity; no TTS implementation or speech-mode enablement is required in S3m.

Define one shared revision/commitment state machine: drafts replace/retract only their active unit; obsolete source revisions invalidate dependent drafts; accepted final units commit once in order; committed output is immutable. Preserve raw ASR hypotheses separately from formatted units. Acoustic ASR finality is not automatic semantic or target commitment. Future TTS consumes only committed targets. Introduce new partial/alignment events in S3b via explicit capability negotiation/versioning; S3m itself preserves existing `sandbox.v2` externally observable behavior.

**M2: Extract capability configuration and processing-plan resolution.** Replace scattered model/profile whitelist branches with a small sandbox capability/configuration registry and registered adapter factories. Declare stable model/profile IDs, pinned revisions/assets/checksums/preparation, supported language/pairs and strategies, partial/revision semantics, incremental-source versus incremental-output support, runtime/platform constraints, cancellation and resource/affinity requirements. Keep metadata descriptive: source partial support must not imply translation token support. Unknown registered adapters remain rejected; configuration does not dynamically execute arbitrary code.

Resolve a requested mode/language/profile into an immutable complete plan before accepting audio. Validate the enabled stage chain, assets, adapter capabilities, formatting policy, decoding/input policies and resource limits; reject incompatible pairs or missing stages with stable errors. No silent substitution. Return the resolved plan/capabilities in `session_ready`, preserving current v2 fields during migration, and pin it for the whole session. A stage adapter may still contain model-specific conversion logic; the transport and orchestrator must not branch on OPUS-MT/M2M100 names. Production `ModelRepository` remains authoritative for installed production assets; sandbox pins are experimental records, not a second production catalog.

**M3: Extract orchestration and configurable resource scheduling.** Move native stage execution/ownership, ordered handoff, bounded queues, finish/ACK/cancel behavior and cleanup out of the WebSocket handler. Migrate one stage at a time with a runnable checkpoint and real-model regression comparison after each migration. Keep socket receive/send independent of native work. Separate the orchestrator's application policy from adapter execution details.

The scheduler owns application executor creation, affinity, admission permits, bounded job queues, deadlines and resource accounting. Adapters declare serial/concurrent use and resource needs, and accept resolved native thread settings; they must not create unmanaged application executors or bypass scheduling. Internal runtime threads may still be created by ONNX/CTranslate2 under these declared settings. Retain per-session ASR state and finite per-job MT admission; do not hold an ordinary production request permit for a session lifetime. Initial MT policy remains global jobs=1 and intra_threads=1. Make these policies configurable with explicit validation, without claiming untested settings are safe. Prepare final-versus-speculative priorities/coalescing/fairness hooks for S3b; enforce native-completion-before-permit-release on timeout/cancel/close. Account for model construction/resident memory as well as jobs, with bounded session admission. Full shared scheduling with production REST pools remains S5; current coexistence evidence is the local guardrail.

**M4: Migrate existing adapters and prove replaceability.** Route current Paraformer/Zipformer online ASR, explicit Silero/SenseVoice utterance ASR and both OPUS-MT/M2M100 translators through the contracts, resolver and scheduler. Preserve current profile choices, transcript/event semantics, client behavior and boundedness during the refactor. First compare two MT profiles using the same source requests without editing handler, wire schema or UI; then exercise a different existing ASR adapter without changing translation, formatter or client code. Normal new-adapter work may add adapter implementation/registration/assets/configuration and contract fixtures, but must not require model-specific edits in the orchestration/transport/UI.

Build a reusable contract verification suite for each real adapter and explicitly labeled fault fixtures: startup/asset failure, language/input limits, partial capability/revisions, source references, output ordering, native exceptions, unsupported cancellation, finish/no-tail-silence, cancel/disconnect during work, idempotent close and resource drain. Runtime/model quality and speed stay separately measured; contract compliance does not establish translation quality equivalence. Retain old protocol and real-model evidence before rerunning; speculative behavior is not enabled in this refactoring checkpoint. Capture shared stage spans with IDs and monotonic clocks so later S3d profiling can extend a common instrumentation path.

**S3m acceptance deliverables:** stage/data/state contracts; model capability configuration and deterministic resolver; transport-neutral orchestrator; configurable managed scheduler; migrated real adapters; passing legacy protocol/browser/real-model/resource regressions and shared adapter checks; documented profile-only MT replacement and ASR adapter substitution evidence; updated module map/reproduction commands. #### S3a — Punctuation and bounded semantic segmentation (after S3m)

- Implement the S3m formatting port and coordinator policy after ASR, retaining the raw transcript alongside the formatted display text and the exact translation-input text. Evaluate a real Chinese/English punctuation/casing adapter with verified assets, license, runtime cost and explicit unavailable behavior. Pure punctuation formatting must preserve lexical content; casing may change English letter case, while number/name normalization is a separate declared policy. Do not infer punctuation quality from punctuated ground-truth oracle input.
- Maintain a bounded mutable tail and finalized readable units. Recompute punctuation on changed tail text with bounded left context; keep accepted units unchanged. Source partial formatting is tentative. Commit a readable unit using source stability, linguistic closure and duration/length limits together, rather than treating each comma, VAD boundary or acoustic final as a sentence.
- Split multiple complete clauses within an acoustic utterance, and merge adjacent forced-duration fragments when needed. Avoid premature cuts in negation, conditional/subordinate clauses, numbers and names. A punctuation prediction does not prove semantic closure. Cap retained context, buffered characters/audio coverage and maximum waiting time; on a limit/finish, produce an explicit forced/incomplete boundary and apply the evaluated finalization policy rather than waiting indefinitely or silently dropping text.
- Preserve source utterance/revision/event references. A text unit may reference spans from one or several ASR utterances; carry text offsets and coarse audio coverage, without claiming word-level timestamps. Give formatted units stable IDs/revisions independent of acoustic utterance IDs. Provide bounded line wrapping and a visibly distinct mutable tail in the browser.
- Acceptance: real unmodified ASR input produces readable captions; punctuation-only lexical preservation holds; existing negation/entity/forced-fragment cases are retained, along with long speech, abbreviations/numbers, late ASR revision, quiet/noise and no-trailing-silence cases. Measure punctuation/boundary quality, raw CER/WER separately, added formatting/commit delay and queue/resource cost.

#### S3b — Earlier source-triggered translation and revisable target text (after S3a)

- Add an evidence-based stable-prefix tracker over successive ASR partials. Repeated agreement for a configurable number of updates and minimum dwell time is a scheduling signal, not proof that ASR cannot revise it. Use a language-aware boundary detector and bounded context to form tentative source units during speech, before an acoustic final. Do not lock the source words merely because a draft translation has started.
- Prefer translating complete short semantic units as they become available. Where a unit is still growing, issue bounded speculative translation snapshots and replace the target draft when the source revision changes. Commit target text only after the source unit is accepted under the measured commitment policy and the final translation has completed; do not irrevocably commit a translated prefix simply because it repeats across drafts. Future words can change target word order and negation scope.
- Extend the S3m typed records/state machine and negotiated wire contract with `target_partial` semantics: translation unit ID, target revision, source unit/revision references, `committed=false` and replacement of the complete draft snapshot. `target_final` commits the unit exactly once. A stale job result must not overwrite a newer draft/final. Committed target units remain ordered and unchanged; the active target draft can be replaced or retracted. Multi-utterance and within-utterance source alignment must be supported by the new schema. Report actual partial support in readiness; preserve the current protocol via an additive negotiated extension or a new version.
- Throttle by both meaningful source change and minimum trigger interval; keep at most one in-flight speculative job and one latest replacement snapshot per session. Coalesce superseded queued drafts. Use bounded/fair scheduling that gives finalization priority over speculation without starving other sessions; retain one global native MT job and one intra-op thread as the initial measured baseline. A superseded executing native call retains ownership until it actually ends; suppress its obsolete output.
- Acceptance: on continuous multi-clause audio, real target drafts appear before the whole acoustic utterance final, follow source revisions and finish as aligned committed units. Test draft retraction, out-of-date results, multi-unit ordering, punctuation changes, finalization during native work, slow/non-ACKing clients, cancel/disconnect and finish with pending drafts. Measure first meaningful target, update gaps, revised-token fraction, discarded draft work and draft/final quality. Do not emulate incrementality by splitting a completed translation into timed characters.

#### S3c — Native incremental decoder output (bounded comparison, after S3b)

Earlier source triggering reduces source waiting; streaming decoder tokens reduces waiting within a single translation job. These are independent improvements. Evaluate real token output from the existing runtime as a separate experiment after source units/revisions work. [CTranslate2's Translator API](https://opennmt.net/CTranslate2/python/ctranslate2.Translator.html) exposes `generate_tokens`, which is not compatible with beam search, and a `translate_batch` per-token callback when `beam_size=1`. The current beam-four adapter cannot be relabeled as token-streaming. Compare deterministic greedy token output with the current beam-four baseline on the same actual source units; do not silently change decoding policy to obtain a streaming label.

Bridge native token callbacks through a bounded thread-safe channel, incrementally detokenize without exposing SentencePiece fragments or language tags, and coalesce target snapshots at a bounded cadence so events do not exhaust the ACK window. Tokens from an unfinished/obsolete job remain drafts, even if its source unit is committed. EOS plus output-bound/quality checks is required before final commitment. Callback cancellation is cooperative; release the native permit only after execution really exits. Keep a measured segment-incremental option if greedy quality fails, explicitly report that decoder-token streaming is unavailable, and evaluate a different adapter only with a new feasibility/quality decision.

S3c completion requires a documented go/no-go comparison of first-token/first-readable-target latency, quality, total inference time, event pressure and cancellation. Acceptance of decoder-token streaming is not required to enter S4 if S3b already provides accepted incremental target captions; it is required before advertising token-streaming capability. Current models still encode finite source snapshots and are not trained/validated simultaneous incremental-source translators.

## P2 — Inference Concurrency and Runtime Safety

**Implemented in the current service.** The application `InferenceQueue` bounds transport reservations and execution deadlines; adapters declare managed admission and own the safe use of runtime instances. `num_threads` controls compute parallelism inside an inference call and does not set API request concurrency. Sherpa recognizers, streams, and TTS objects remain inside the adapter boundary.

The standard Sherpa adapters use a shared `ElasticRuntimePool` lifecycle and admission implementation. Calls sharing one native runtime remain serialized by the existing adapter lock; separate adapter instances can run concurrently. Instance construction is lazy, defaults to a retained minimum of one and a maximum of two per model, and uses two constructor threads per instance. The per-model waiting limit defaults to four. `max_concurrent_inference=1` enables adapter-managed parallel inference; `0` selects the serial global queue. Existing Sherpa behavior and native code were left unchanged. Qwen3-TTS still uses one native backend runtime; this pool does not enable Qwen batching or process parallelism.

Same-model capacity is measured with the fixed-arrival HTTP harness, which compares delivered rate, valid-response success, complete-response P90, per-window latency/wait, and queue drain, alongside CPU/RSS and instance warm-up. Do not use closed-loop worker counts as a capacity result. The current macOS reports record passing rates of 14 req/s for SenseVoice and 8 req/s for Matcha. Supertonic passed the observed checks at 1.9 req/s, but its 1,000-request sample is below the formal 3,000-request minimum. These measurements cover named models and inputs on one machine; same-instance safety and performance still require validation for each runtime type and target platform.

ASR `decode_streams()` micro-batching remains an optional research direction. It is not part of the production concurrency path; any future experiment must account for added batching latency and verify transcript equivalence before adoption.
