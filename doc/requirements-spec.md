# SmartVoice 本地 STT/TTS 一体化服务：需求规格说明书

- **版本：** 0.1（调研后需求基线）
- **日期：** 2026-09-27
- **状态：** 按 2026-09-27 用户重新定义目标后的修订版
- **关联文档：** [业界调研](industry-research.md)

## 0. 最新目标定义（取代本文档中冲突的旧目标）

1. **轻量化与边缘优先：** 面向 PC、智能手机等资源受限设备。轻量指标须同时看安装包、模型体积、常驻内存/显存、首包延迟和能耗，不以“参数小于 7B”单独判定轻量。
2. **多平台演进：** 目标平台包括 Windows、macOS、Linux、Android；第一阶段只交付 Windows。后续平台共享 API/能力定义，但推理后端、模型格式和硬件加速按平台适配。
3. **多语言：** 支持中文、英语及可扩展的其他语言；中文和英语为第一阶段优先语言。语言覆盖按具体 STT/TTS 模型分别声明，不要求单个模型覆盖所有语言。
4. **Agent 友好 Web API：** 提供稳定 HTTP API。接口采用 OpenAPI 规范描述，STT/TTS 路径和字段优先兼容 OpenAI Audio API 常用约定；有需要时提供 MCP Server 作为 Agent 工具适配层。
5. **前后端解耦：** 前端及 API 客户端依赖稳定、版本化的公开契约；服务端可以更换推理后端、模型格式或 runtime，而无需修改前端交互或 API 使用方式。
6. **平台与硬件解耦：** 核心业务逻辑独立于操作系统、CPU/GPU 厂商和硬件架构；通过平台/设备适配层承接差异。第一阶段实现 Windows，后续扩展 macOS、Linux、Android。
7. **框架定位：** sherpa-onnx 是首选候选推理引擎之一，但需以其本身能力与本产品 API/模型管理/安装体验要求做差距评估，不预设它单独满足完整产品目标。

本节优先于本文档旧版本中的 Windows/Linux 同批首发、7B 模型筛选作为主目标及将 OpenAI 风格 API 视为唯一接口策略等内容。

## 1. 背景与问题陈述

目标用户需要在普通个人电脑上离线使用语音识别和语音合成。当前用户通常要分别安装 STT、TTS 项目，处理不同 Python/CUDA 环境、模型仓库、下载和 API，无法用一套简单的本地服务完成两类任务。

成熟组件已经分别具备相当多的能力，甚至 sherpa-onnx 已覆盖两类推理；本项目应聚焦把它们组织成可安装、可管理、接口统一、可审计的桌面/本地服务产品。

## 2. 产品目标

1. 提供单机本地 STT + TTS 推理服务，推理期间完全离线可工作。
2. 支持 CPU；在兼容硬件和软件依赖存在时支持 GPU 加速，并清楚报告实际设备。
3. 支持经项目验证的主流小模型。`<7B` 是模型目录的规模上限约束，不是硬件可用性承诺；各模型必须给出最低建议 RAM/VRAM 和性能基准。
4. 内置可浏览的候选模型目录，提供公开来源下载、校验、安装、切换、删除及离线导入。
5. 以稳定的本地 Web API 向其他应用和 Agent 提供能力，采用 OpenAPI 描述并兼容常用音频 API 约定。
6. 尊重模型、代码和声音数据许可，并将本机隐私作为默认行为。

## 3. 非目标

首期不建设模型训练/微调平台、云端托管 API、账号/付费系统、多机集群调度、通用任意模型运行器、实时同传/翻译产品或浏览器完整 UI。不得承诺全部模型在普通 CPU 上达到实时速度，也不得承诺任意显卡/驱动组合开箱即用。

## 4. 用户与主要场景

- **个人用户：** 下载程序后用 CPU 完成本地中文/英文转写和文本朗读。
- **GPU 用户：** 安装/选择 CUDA 可用运行时，选用更高质量模型，并确认任务确实在 GPU 上执行。
- **开发者：** 通过本机 REST API 集成语音输入、朗读、转写批处理。
- **受限网络用户：** 从可访问的公开模型源下载，或导入离线模型包；断网后继续推理。

典型流程：安装应用 → 首次启动选择 CPU/GPU → 在模型目录查看模型卡/许可/空间/设备 → 下载模型 → 调用 STT/TTS API → 查询状态、换模型或删除模型。

## 5. 架构约束与扩展边界

### 5.1 前端与推理后端接口

前端包括 Web 管理界面、CLI、桌面壳及外部 Agent/client。它们只通过版本化的公开 HTTP API（以及明确版本化的实时音频 WebSocket 协议）与服务通信，不直接链接推理框架、访问模型文件或依赖某个 runtime 的专属参数。

服务端定义稳定的领域契约和后端适配器接口。适配器负责把统一请求映射为具体模型/runtime 调用，并将结果、错误、取消和能力描述映射回统一结构。替换 sherpa-onnx、ONNX Runtime、其他原生引擎或新增模型格式时，前端 API 和交互保持不变；只有公开能力发生有意的版本化变化时才更新客户端。

适配器至少抽象：模型加载/卸载、STT、TTS、流式能力、语言/voice、输入输出格式、设备选择、取消、健康检查与错误分类。前端根据 capability 查询可用功能，不能依据后端名称推测功能。

### 5.2 平台与硬件接口

核心领域层不得直接调用 Windows 专属 API、POSIX API、CUDA API、音频设备 API 或 CPU 特定指令。通过接口提供：应用数据目录、配置/日志、进程生命周期、音频编解码、设备枚举、计算设备探测、资源状态、模型文件访问和平台服务启动。

运行时设备统一表示为 `auto`、`cpu` 和可扩展的设备描述（如 CUDA GPU、DirectML、Core ML、Android NNAPI 等）。设备能力由 runtime/provider 插件报告；业务逻辑不硬编码 NVIDIA/CUDA 分支。某平台不支持某 provider 时，capability 返回不可用及原因，CPU 回退行为显式可见。

第一阶段只需实现 Windows 平台适配器和经过验证的 CPU/GPU provider；但核心代码、模型元数据、API schema、任务调度和模型管理不得把 Windows 或特定芯片假设写入领域层。每个后续平台需新增适配器和兼容性验证，不应重写 API/业务核心。

Android 等移动端可选择嵌入式 SDK/API 方式，而非运行常驻 Web 服务；复用的是领域契约、模型能力描述和任务语义，不要求所有平台采用相同进程形态。

## 6. 范围与优先级

### P0：首个可用版本

- Windows x64 为唯一第一阶段目标平台；CPU 必须支持，GPU 按验证矩阵提供可选加速。核心逻辑须通过平台适配接口运行；macOS、Linux、Android 属后续平台。
- 本机单用户 REST API；默认仅监听 loopback。前端仅依赖公开 API，不与推理 runtime 耦合。
- 文件 STT：常见 WAV/MP3/M4A/FLAC（格式清单按解码器实测）；首发验收重点为中文和英语，同时目录架构应支持后续增加其他语种模型。
- 非流式 TTS：首发优先提供中文和英语语音，返回 WAV；采样率、声道、模型 voice 明确。模型目录可按需增加其他语言语音。
- `GET /health`、`GET /v1/models`、`POST /v1/audio/transcriptions`、`POST /v1/audio/speech`。
- 默认模型目录至少含一个轻量 STT 和一个轻量 TTS；候选优先 sherpa-onnx CPU 模型，并根据中文质量实测增补 FunASR 或 CosyVoice 等可选模型。
- 模型下载/取消/续传或失败恢复、校验、安装、激活、卸载、磁盘空间提示和离线导入。
- CPU/GPU 自动选择与显式设备模式；实际设备可查询。
- README/API 文档/模型许可和网络需求说明。

### P1：扩展

- Windows 上可选 GPU 加速运行时；按已验证的 GPU/驱动/运行时矩阵发布。
- 实时流式 STT（仅限支持流式的模型），通过 WebSocket 或分块 HTTP 明确返回 interim/final 结果。
- 多语言模型、时间戳、VAD、说话人分段/标记、标点与热词（按后端支持程度）。
- 高质量 TTS 与多说话人/风格参数；受控的参考音频克隆只有完成许可、授权与隐私设计后再提供。
- ModelScope 等镜像 provider、模型包导入/导出、应用托盘或轻量 Web 管理 UI。

### P2：后续探索

- macOS、Linux、Android 端侧适配；Apple Silicon、AMD GPU、DirectML/Vulkan 等后端；并发服务、多用户权限、插件 SDK、自动性能调优。Android 优先评估嵌入式 SDK/JNI 与应用内调用，是否提供 localhost Web 服务需考虑移动系统后台限制。

## 7. 功能需求

### 7.1 安装、启动和本地服务

- **FR-001** 安装过程不得强制要求 Python、编译器或 GPU 环境由用户预先配置；若首期采用 Python 分发，应打包/隔离受支持运行时并记录其版本。
- **FR-002** 首次运行提供 CPU/GPU 检测结果、服务地址和模型目录路径；GPU 不兼容时能继续 CPU 模式。
- **FR-003** 默认只绑定 `127.0.0.1`/`::1`，不得默认暴露 LAN。用户显式启用远程监听时必须显示风险提示，并支持 API token。
- **FR-004** 服务退出应释放模型和端口；重复启动应给出已有实例信息而非静默覆盖配置。
- **FR-005** 所有设置可从配置文件或 CLI 修改，日志不得记录完整识别音频/合成文本内容（默认脱敏）。
- **FR-006** 前端只能依赖有版本的公开 API/capability 契约；不得绑定后端 SDK、内部类型、模型目录布局或 runtime 私有参数。后端切换不得要求前端改动。
- **FR-007** 核心业务通过平台服务接口访问文件系统路径、配置、日志、设备、生命周期和音频 I/O；Windows API/硬件 vendor API 只允许出现在对应适配器中。
- **FR-008** 平台适配器/provider 必须报告支持能力、版本、设备和失败原因；服务不得把运行时回退隐藏为原设备执行成功。

### 7.2 模型目录和生命周期

- **FR-010** 每个目录项目展示：名称、任务、架构/参数量（可知时）、支持语言、流式能力、精度/量化、后端、下载大小、安装后占用、建议 RAM/VRAM、来源和固定 revision、许可证、已知限制。
- **FR-011** 来源只允许 HTTPS 和本地文件；目录定义可更新，但运行时不得擅自执行仓库脚本或模型中的任意代码。优先使用 safetensors/ONNX 等受支持安全格式；需要 `trust_remote_code` 的模型须独立审核并默认禁用。
- **FR-012** 下载采用临时目录；校验文件大小及哈希成功后原子安装。支持取消、断点续传、重试、限速可选、错误可读、无效部分清理。
- **FR-013** 可按任务查看、安装、激活、停用和删除模型；删除前提示路径与空间释放量，不能删除当前使用中的文件。
- **FR-014** 提供离线模型导入与目录导出清单；导入仍执行格式、路径、哈希和许可元数据检查。
- **FR-015** 模型加载失败返回模型 ID、后端、设备、阶段与用户可执行建议，不回显密钥或私人路径中的敏感片段。
- **FR-016** 同时加载多个模型是可选项；首版最低要求允许配置每任务一个活动模型。切换模型要有加载中状态且失败后保留原活动模型。

### 7.3 STT

- **FR-020** 支持音频文件上传和可选本地文件路径模式（后者默认关闭，防路径越权）；接受格式、最大文件大小、时长、采样率在 API 文档明确。
- **FR-021** 请求可指定 model、language（auto/语言代码）、返回格式、时间戳与可选领域参数；未知参数返回 4xx，不静默忽略关键设置。
- **FR-022** 响应包含文本、模型 ID、检测/指定语言、音频时长；如支持则含段落时间戳、置信度和说话人标记。缺失字段不得伪造。
- **FR-023** 文件过长时分段/VAD 策略有上限和错误说明；任务超时/取消后释放临时文件。
- **FR-024** 流式仅对声明流式能力的模型可用。输出区分 partial/final，带序号；断连后清理会话。

### 7.4 TTS

- **FR-030** 输入文本、模型、voice、语言、格式、采样率以及模型支持的速度/风格；不支持的参数返回可读错误。
- **FR-031** 响应为可直接保存/播放的音频，首版 WAV；扩展格式另行验收。提供内容类型、时长、采样率和模型元数据。
- **FR-032** 长文本有字符数限制、分句策略和输出时长/文件大小保护；超限返回建议拆分。
- **FR-033** 可查询模型支持的 voice 列表；每个预置 voice 来源/许可随模型记录。
- **FR-034** 参考音频/克隆能力默认关闭，待模型许可、声纹授权、存储清理和滥用控制要求批准后开放。

### 7.5 状态、配置和可观测性

- **FR-040** 提供存活/就绪状态、版本、运行时版本、设备检测、已安装/活动模型、资源状态端点。
- **FR-041** 请求日志给出 request ID、时长、状态码、模型及实际设备，不默认记录文本、音频、参考音频或 token。
- **FR-042** 配置模型目录、缓存路径、日志级别、CPU 线程数、设备、并发队列和 API 监听地址。
- **FR-043** GPU 初始化错误应可诊断（未找到 GPU、驱动不匹配、缺运行时、显存不足、模型不支持），允许用户显式重试 CPU。

## 8. API 草案

### `POST /v1/audio/transcriptions`

`multipart/form-data` 字段：`file`（必填）、`model`、`language`、`response_format=json|text|verbose_json`、`timestamps`。

JSON 示例：

```json
{
  "text": "今天的会议开始了。",
  "language": "zh",
  "duration": 2.84,
  "model": "stt-sensevoice-small-int8",
  "device": "cpu",
  "segments": []
}
```

### `POST /v1/audio/speech`

JSON 字段：`input`（必填）、`model`、`voice`、`language`、`response_format`、可选 `speed`。
返回音频二进制；错误采用稳定 JSON 错误结构和 request ID。

### 管理端点（本项目扩展）

- `GET /health`：服务存活。
- `GET /ready`：API 就绪及模型状态。
- `GET /v1/models`：本机已安装模型与 capability。
- `GET /v1/catalog`：经验证的可安装目录（含 revision/许可/资源/源）。
- `POST /v1/models/{id}/download`、`DELETE /v1/models/{id}`、`PUT /v1/models/{id}/activate`。
- `GET /v1/runtime`：CPU/GPU/运行时和实际选择。
- 长任务如下载可返回 `job_id`，用 `GET /v1/jobs/{id}` 查询状态。

API 必须提供 OpenAPI 文档、大小/超时限制、错误码、文件清理行为和版本兼容策略。下载 API 不接受任意 URL，以防 SSRF；只可选目录登记的 source 或导入本地文件。

## 9. 非功能需求及可验收指标

### 9.1 性能与资源

- **NFR-001 CPU 可用性：** 在发布的最低参考机型上，STT 与 TTS 均完成端到端任务且不依赖 GPU；公布每模型实时因子（处理秒/音频秒）、TTFA（首音频延迟）和内存峰值。
- **NFR-002 GPU 真实性：** 指定兼容矩阵内执行时，状态/日志能够证明设备为 GPU；超出矩阵应拒绝或显式 CPU 回退并通知。
- **NFR-003** 对每个目录模型，在至少一台参考 CPU 与一台参考 NVIDIA GPU 上记录启动时长、吞吐、峰值 RAM/VRAM、模型体积和质量测试结果。硬件型号/驱动/软件版本随报告发布。
- **NFR-004** 不设空泛“普通 PC 实时”承诺。产品发布前由产品确定最低规格及可接受的 RTF/延迟阈值。
- **NFR-005** 单请求、排队和并发资源有上限；模型卸载后显存/内存可回收或提供重启建议。

### 9.2 稳定性、安全和隐私

- **NFR-010** 推理请求不要求互联网连接；断网条件下已安装模型可完成 STT/TTS。
- **NFR-011** 默认 loopback 绑定，无音频/文本遥测；LAN 监听需显式配置和鉴权。
- **NFR-012** 限制上传大小、时长、并发、临时目录访问；防任意路径读取、任意 URL 下载、目录穿越及过量资源耗尽。
- **NFR-013** 对模型下载启用 TLS 校验、固定 revision、文件哈希；安装不执行不可信模型仓库自定义代码。
- **NFR-014** 临时音频清理策略可配置且默认在请求完成后删除；日志默认不留请求内容。
- **NFR-015** 模型许可、来源和版本可从 UI/API 导出，发行包附第三方声明。

### 9.3 可维护与可扩展

- **NFR-020** API schema 版本化；适配器 capability schema 有版本，未知字段拒绝或忽略规则明确。
- **NFR-021** 模型目录数据与服务版本解耦，但每次加载仍校验 schema、哈希和后端兼容性。
- **NFR-022** 新增一个适配器不要求修改公开 API；适配层有统一异常类型、日志字段与取消语义。
- **NFR-023** 支持配置目录迁移与备份；升级不自动删除模型或覆盖用户配置。
- **NFR-024** 核心领域模块可在不加载 Windows/特定 GPU 适配器的情况下构建和执行平台无关逻辑；新增平台/provider 以实现接口和兼容性声明为主，不修改 API 领域契约。

## 10. 模型目录初始建议

初始目录是候选而非已承诺支持；需用固定版本实测并完成许可审核后标记“已验证”。

| ID | 任务 | 候选 | 后端方向 | 初始分组 |
|---|---|---|---|---|
| `stt-sensevoice-small-int8` | STT | SenseVoiceSmall | FunASR 原生或 sherpa-onnx 对应 ONNX 包 | 中文优先轻量候选 |
| `paraformer-zh-local` | STT | Paraformer 中文模型 | FunASR 或兼容 sherpa 模型 | 中文备选 |
| `whisper-small-local` | STT | Whisper small/base | faster-whisper 或 whisper.cpp | 多语言可选 |
| `piper-voice-*` | TTS | 按许可登记的 Piper voice | sherpa-onnx/Piper | CPU 轻量候选 |
| `kokoro-local` | TTS | Kokoro 及明确版本的 ONNX 转换模型 | ONNX Runtime/sherpa 适配（须确认支持） | 轻量自然度候选 |
| `cosyvoice2-0.5b-local` | TTS | CosyVoice 2 0.5B | PyTorch 适配器 | 高质量可选 |
| `qwen3-tts-0.6b-local` | TTS | Qwen3-TTS 0.6B 子模型 | PyTorch/官方推理栈 | 高质量可选 |

目录审查必须记录每个具体文件仓库的来源与许可。模型参数量作为目录元数据记录，不作为轻量验收的唯一阈值；同时记录模型体积、依赖体积、冷启动时间、峰值内存、延迟、能耗（可测时）和平台兼容性。

## 11. 验收标准

首个版本发布前至少满足：

1. 在干净 Windows 参考环境安装启动；无 GPU 环境中完成 STT 与 TTS。后续平台分别建立验收矩阵，不作为第一阶段阻塞项。
2. 使用至少两个不同后端/provider 的契约测试或替身验证，切换推理后端不要求更改前端/API 客户端。
3. 核心领域层构建/运行不直接依赖 Windows 或 GPU vendor API；平台专属依赖只出现在适配器。
4. 下载目录模型时显示来源、许可、大小、进度；错误哈希不能进入可用状态；下载后断网仍可推理。
5. 用支持的 GPU 环境证明请求确实由 GPU 执行；禁用/移除 GPU 后 CPU 模式仍工作。
6. REST API schema、错误码、文件边界和示例可按文档调用；取消、超时与并发队列按定义回收资源。
7. 测试样例覆盖中文/英语及首批扩展语言、静音/损坏/超长音频、空文本、超长文本、模型缺失、磁盘不足、网络中断、显存不足、设备回退。
8. 隐私检查确认监听地址、日志和临时音频符合默认本地策略。
9. 每个展示为“已验证”的模型有质量样例、性能基准、来源 revision、哈希、许可证和硬件要求。

## 12. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 单一轻量模型无法覆盖中文质量、跨语言和实时流式全部目标 | 用户误以为覆盖度完整 | 用 capability 驱动选择；明确“轻量/高质量/流式”差别，分层目录。 |
| PyTorch/CUDA 依赖冲突和发行包体积 | 安装失败、维护成本高 | CPU 核心路径独立；CUDA 高质量后端可作为可选组件，发布已验证矩阵。 |
| Hub 网络不可达/下载中断 | 首次体验失败 | 多 provider、镜像设置、续传、离线导入；不捆绑巨量权重。 |
| 模型许可或语音权利不清 | 法律与分发风险 | 模型级法律审查；目录分发与自动下载同样展示许可证；默认不纳入条款不明模型。 |
| 参数量不能代表资源需求 | OOM/低速 | 以实测内存、RTF、延迟和最低硬件为准，参数量仅筛选条件。 |
| 语音克隆存在未授权冒用风险 | 个人权利与滥用 | 首版关闭克隆；需要明确同意、保留期和滥用治理后另行评审。 |
| 适配模型格式版本变动 | 升级破坏用户环境 | 固定 revision/哈希，回归已验证组合，版本化目录及适配器。 |

## 13. 需要产品决策的事项

以下为进入实现前的待定项，建议产品负责人确认：

1. Windows 第一阶段的最低支持版本及架构（x64 是否唯一）是什么？
2. 除中文和英语优先外，首批还需验收哪些具体语种？
3. 最低参考配置：CPU、RAM、磁盘和 GPU/VRAM 的验收机型是什么？
4. 性能目标：文件 STT 最大时长、可接受 RTF；TTS 首包延迟及长文本吞吐目标是什么？
5. OpenAI Audio API 兼容需要覆盖哪些字段/响应格式？是否首期同步交付 MCP Server？
6. GPU 首期只要求 NVIDIA CUDA，还是必须同步覆盖 AMD/Intel？
7. 允许的模型许可证范围：是否要求所有目录模型均允许商用/可再分发？
8. 模型获取优先级：Hugging Face、ModelScope、可配置镜像和本地导入中哪些必须首发？
9. UI 形态：仅 CLI/REST，还是首期需要桌面托盘/模型管理 Web UI？
10. 是否接受 Python CPU 核心 + 可选较大 GPU 运行时的多组件安装策略？

## 14. 建议的下一步

先由产品确认第 12 节关键约束，然后冻结 Windows 首批 STT/TTS checkpoint/revision 与目标硬件。用参考 PC 做资源、质量和延迟对比，完成许可审查及 OpenAPI/MCP 范围决策后，形成实现设计和后续平台兼容矩阵，再进入原型开发。
